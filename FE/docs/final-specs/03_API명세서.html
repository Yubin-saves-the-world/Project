API 명세서

전체 96개. 기능별로 묶고, 보내는 값·받는 값·실패했을 때를 한 곳에 모았습니다.

앱과 서버가 주고받는 요청과 응답입니다. 기능 순서로 묶었고, MVP 35개는 처음부터 펼쳐져 있습니다. 2차 35개 · 확장 26개는 눌러서 펼칩니다. 어떤 기능이 왜 필요한지는 기능 명세서에 있습니다.

먼저 알아둘 것

주소모든 경로는 /api로 시작합니다. 개발 중 주소는 http://localhost:8080, Android 에뮬레이터에서는 http://10.0.2.2:8080
형식JSON(UTF-8), 필드 이름은 snake_case. 사진과 게시글 이미지만 multipart/form-data
로그인헤더에 Authorization: Bearer {access_token}. 토큰은 7일이고 재발급은 없습니다. 만료되면 401 → 다시 로그인
받는 값필드는 항상 있습니다. 값이 없으면 null, 목록은 []. 목록은 { items, page, page_size, total }
시간날짜 2026-10-06, 시각 2026-10-06T19:02:10+09:00(한국 시간). 한 주는 월요일부터
실패{ code, message, status, fields }. 앱은 code로 나누고 message는 그대로 보여줘도 됩니다
모든 API 공통 실패400 VALIDATION_FAILED(입력 오류, fields에 칸별 사유) · 401 UNAUTHORIZED(토큰 없음·만료·탈퇴) · 403 FORBIDDEN(관리자 전용) · 403 ONBOARDING_REQUIRED(신체정보 등록 전)
내 것이 아닌 데이터404 NOT_FOUND (남의 데이터가 있는지도 알려주지 않습니다)
분석은 기다리는 방식요청하면 바로 202로 접수하고, 앱이 GET /body-analyses/{id}를 2초마다 최대 60초 조회합니다. 분석 실패(failed)도 HTTP 200입니다

처음부터 끝까지 부르는 순서

① POST  /api/users                    가입 (토큰은 오지 않음)
② POST  /api/auth/login              로그인 → access_token
③ POST  /api/users/me/profile        신체정보 → 온보딩 끝
④ POST  /api/photos                  사진 올리기 → photo_id
⑤ POST  /api/goal-bodies             (선택) 목표 체형
⑥ POST  /api/body-analyses/photo     분석 요청 → 202, analysis_id
⑦ GET   /api/body-analyses/{id}      2초마다 확인 (pending → done / failed)
⑧ POST  /api/routines                { analysis_id } → 오늘부터 7일 루틴
⑨ GET   /api/routines/today          홈의 오늘의 루틴
⑩ POST  /api/workout-logs            운동 시작 (종목 1개)
⑪ POST  /api/workout-logs/{id}/sets  세트마다 기록 (client_set_id)
⑫ PATCH /api/workout-logs/{id}/complete  운동 종료

표의 *는 꼭 보내야 하는 값, null 가능은 값이 없을 수 있다는 뜻입니다. 예시의 값은 모양을 보여주는 용도입니다.

알아둘 것

  • 가입만 하고 토큰은 발급하지 않는다. 앱이 이어서 POST /auth/login을 호출한다.
  • 이메일은 소문자로 바꿔 저장·비교한다.
  • 동의 4개(terms_agreed, privacy_agreed, body_photo_agreed, ai_processing_agreed)가 모두 true가 아니면 TERMS_REQUIRED. 앱은 사진·AI 동의를 한 체크박스로 묶어 두 값을 함께 보내도 된다.
  • 동의는 종류별(terms·privacy·body_photo·ai_processing)로 약관 버전과 시각을 이력으로 남긴다. 마지막 기록이 현재 상태이고, 철회해도 이전 기록은 지우지 않는다.
  • 비밀번호는 BCrypt로 해시해 저장하고 응답·로그에 남기지 않는다.

서버가 하는 일 (처리 순서)

  1. 요청 검증: 이메일 형식, 비밀번호 규칙, 닉네임 2~20자, 동의 4개가 모두 true → 실패하면 VALIDATION_FAILED / TERMS_REQUIRED.
  2. 이메일을 소문자로 바꿔 users에서 중복 확인 → EMAIL_DUPLICATED. 닉네임 중복 → NICKNAME_DUPLICATED.
  3. 한 트랜잭션으로 users 1행(BCrypt 해시)과 user_consents 4행(agreed=true, source=signup, 약관 버전)을 넣는다.
  4. 동시 가입으로 UNIQUE 위반이 나면 2번과 같은 중복 에러로 바꿔 돌려준다.
  5. 201. 토큰은 주지 않는다(앱이 이어서 로그인).

  3. JWT를 발급한다(7일, 회원 ID·권한 포함).
  4. onboarding_completed는 user_profiles에 행이 있는지로 계산해 함께 돌려준다.

  2. photo_id(정면)·side_photo_id(측면)가 내 사진이고 삭제 요청이 없는지(NOT_FOUND), type=current인지(PHOTO_TYPE_MISMATCH) 확인한다.
  3. goal_body_id가 있으면 내 목표인지 확인한다(NOT_FOUND).
  4. body_photo와 ai_processing 동의가 모두 현재 true인지 확인한다 → 아니면 CONSENT_REQUIRED.
  5. 목표가 있으면 status='done'인지 확인한다 → 아니면 GOAL_NOT_READY.
  6. 이미 pending인 분석이 있으면 ANALYSIS_IN_PROGRESS(기다리는 사용자에게 "횟수 초과"를 먼저 보여주지 않으려고 한도보다 먼저 검사).
  7. 하루 한도: 오늘(KST) 만든 pending·done 분석이 3개 이상이면 ANALYSIS_QUOTA_EXCEEDED.
  8. body_analyses에 status='pending' 행을 넣는다. 위 6번과 동시에 들어온 요청은 uq_analysis_one_pending이 막으므로 같은 ANALYSIS_IN_PROGRESS로 바꿔 돌려준다.
  9. 커밋이 끝난 뒤(afterCommit) 비동기 작업을 시작하고 202를 돌려준다.
  10. 작업: S3에서 사진을 읽어 FastAPI /analyze 호출(품질 검사 → MediaPipe 수치 → 목표가 있으면 Qwen-VL 비교). 성공하면 수치·판정·AI 소견을 UPDATE하고 done, 품질 실패·AI 오류면 failed와 error_code.
  11. 정리 작업(@Scheduled)이 90초 넘은 pending을 failed(AI_TIMEOUT)로 바꾼다. 늦게 도착한 AI 결과는 status='pending'일 때만 반영한다.

알아둘 것

  • 즉시 로그인이 불가능해야 하고, 이메일·닉네임·신체정보·사진 원본·분석·운동 기록 등 개인정보를 삭제한다 (Google Play 계정 삭제 요건).
  • 토큰은 7일짜리 JWT라서, 모든 요청에서 탈퇴한 회원인지 확인해 UNAUTHORIZED로 막는다. 토큰이 아직 만료되지 않았어도 탈퇴 직후 접근이 끊겨야 한다.
  • 사진 원본은 저장소(S3)에서 실제로 지운 것을 확인한 뒤 완료로 본다. 지우지 못한 파일은 접근을 막은 채 재시도하고, 24시간 안에 지우는 것을 목표로 한다.
  • 같은 이메일로 다시 가입할 수 있어야 한다.
  • 작성한 게시글·댓글은 작성자 표시를 "탈퇴한 사용자"로 바꾸고 남길지, 함께 삭제할지 정해야 한다 (7장 결정 ⑨).

서버가 하는 일 (처리 순서)

  1. users.status='withdrawn'으로 바꿔 즉시 접근을 막는다(이후 모든 요청은 UNAUTHORIZED).
  2. 한 트랜잭션으로 탈퇴 시 처리 표의 테이블을 정리하고, users의 이메일·비밀번호·구글 ID·카카오 ID를 NULL, 닉네임을 withdrawn_{id}로 바꾼다.
  3. 카카오 계정이면 카카오의 연결 끊기(POST /v1/user/unlink)를 호출한다. 실패해도 탈퇴는 진행하고 재시도 대상으로 남긴다.
  4. S3의 사진 파일을 지우고 삭제를 확인한다. 실패한 파일은 photos.deleted_at으로 접근을 막은 채 재시도한다(24시간 안에 완료가 목표).
  5. 204.

부록. 상태가 바뀌는 규칙

대상 상태 흐름 규칙
분석 body_analyses.status pending → done · failed 접수하면 pending. AI가 끝나면 done, 품질 실패·AI 오류·90초 초과면 failed(AI_TIMEOUT). 끝난 분석은 바뀌지 않고, 다시 분석하면 새 행이 생긴다. pending은 사용자당 1건.
목표 체형 goal_bodies.status pending → done · failed (사진을 바꾸면 done→pending) 사진으로 등록하면 pending, 설명만이면 바로 done. 특징 추출이 끝나면(성공·실패 모두) 목표 사진은 삭제된다. pending 중에는 이 목표로 분석할 수 없다(GOAL_NOT_READY).
루틴 routines.status planned → done · skipped done은 서버가 자동으로 바꾼다(루틴의 모든 종목에 종료된 운동 기록이 생길 때). skipped는 사용자가 PATCH로 바꾼다. 둘 다 되돌릴 수 없고, 루틴을 다시 만들어도 유지된다.
운동 기록 workout_logs.status in_progress → completed · aborted 시작하면 in_progress. PATCH …/complete면 completed, 6시간 넘게 끝나지 않으면 서버가 aborted. 같은 종목의 in_progress는 1개뿐이다. aborted는 통계·연속 기록에서 제외.
루틴 수정 제안 routine_suggestions.status pending → applied · dismissed confirm으로 처리한다. 생성 24시간 뒤(expires_at)에는 SUGGESTION_EXPIRED. 이미 처리했으면 SUGGESTION_ALREADY_HANDLED.
신고 reports.status pending → resolved · rejected 서로 다른 신고자 3명이 pending이면 대상을 자동으로 숨긴다. resolved는 숨김 유지, rejected는 숨김 해제.
