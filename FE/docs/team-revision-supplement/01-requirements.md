# 기능·화면·예외 처리 보완

이 문서의 규칙은 팀장 수정본의 같은 F-ID에 덧붙이거나 충돌 문구를 교체한다. KST는 Asia/Seoul 기준이며 날짜 귀속은 서버가 계산한다.

## F-01·F-02·F-11: 동의와 인증

1. 가입에 필수인 동의는 약관·개인정보 처리 2종이다. 사진·AI 동의는 별도 선택 항목으로 받으며, 가입 단계에서 각각 켜거나 끌 수 있다. Google 신규 가입에도 같은 기준을 적용한다.
2. `consent_completed`는 약관·개인정보 필수 동의 완료만 뜻한다. 사진·AI 동의는 각 플래그로 판단한다. 프로필 입력 완료 여부는 기존 `onboarding_completed`를 유지한다.
3. 앱 진입 순서: 로그인 확인 → 필수 동의 확인 → 프로필 확인 → 홈. 사진·AI 동의 철회로 홈·운동·기존 기록 조회를 막지 않는다.
4. 사진 업로드에는 사진 동의, 사진 AI 분석·목표 사진 처리에는 사진 동의와 AI 동의, 글 분석·AI 코치에는 AI 동의가 필요하다. DB 규칙으로 기존 결과의 루틴을 생성하는 것은 새로운 AI 처리가 아니므로 AI 동의 철회 후에도 허용한다.
5. 사진 동의 철회는 새 업로드와 새로운 사진 처리 요청을 막는다. AI 동의 철회는 새 AI 요청을 막는다. 각 동의를 필요로 하는 pending 작업은 실패 처리하고 늦은 결과를 저장하지 않는다. 기존 결과는 계속 조회 가능하다. 사진 삭제는 별도 삭제 동작으로 안내한다.
6. JWT 7일·Refresh Token 없음·로그아웃 시 앱 토큰 제거 정책을 유지한다. 모든 인증 요청은 회원 존재·탈퇴 상태·`token_version`을 확인한다. 비밀번호 재설정 성공 시 버전을 증가시켜 기존 JWT를 모두 무효화한다. 로그아웃 자체는 현재 토큰만 서버에서 폐기하는 기능이 아니다.
7. 가입은 토큰 없는 201, 이어서 로그인하는 원문 흐름을 유지한다. 로그인 실패 시 가입을 다시 시도하지 않고 로그인 화면으로 안내한다.

## F-04·F-05·F-06·F-14: 사진·분석·목표

### 분석 결과 불변 조건

- `pending`: 결과 필드는 null, 결과 배열은 빈 배열, 오류 필드는 null.
- `done`: 오류 필드는 모두 null. 완료 후 저장된 결과는 목표·프로필 수정으로 다시 계산하지 않는다.
- `failed`: 오류 코드·메시지·종료 시각이 있고 결과 필드는 null, 결과 배열은 빈 배열.
- `source=photo`: `text_summary=null`. 측면 입력이 없으면 `neck_forward_deg=null`이고 측정 불가 사유는 SIDE_PHOTO_MISSING이다.
- `source=text`: 사진 ID·측정값·점수·체형 유형은 null, 판정 배열은 빈 배열. 요약은 `text_summary`에 저장한다. 원문의 글 분석이 목표 비교를 지원하지 않는 범위는 유지한다.
- 사진 참조 ID가 삭제로 null이 되어도 이미 계산한 측정값은 유지한다. 따라서 null인 사진 ID만 보고 과거에 측면 입력이 없었다고 판단하지 않는다. 입력 여부는 저장된 입력 스냅샷으로 확인한다.
- 산식 미검증 시 점수는 null, 판정은 unavailable/PROFILE_NOT_VALIDATED다. 측정값 자체가 유효하면 유지한다. 측정 불가 배열은 실제 측정값이 null인 항목만 나열한다. 측정 실패 사유와 판정 미검증 사유를 혼동하지 않는다.
- 골격 비율의 체형 분류 기준도 미검증이면 `body_type=null`이다. AI 비교는 외형에 대한 의견과 운동 선호를 표현하며 근육량·등 두께를 측정한 사실처럼 표현하지 않는다.

### 목표와 비동기 경쟁 방지

1. 사용자당 현재 목표 1행을 유지한다. pending 목표의 PATCH는 `409 GOAL_PROCESSING`으로 거절한다.
2. 요청별 작업 식별자와 목표 revision을 저장한다. 결과 반영 시 같은 작업인지, 목표가 존재하는지, 상태가 pending인지, 필요한 동의가 여전히 유효한지 확인한다.
3. pending 목표 삭제·동의 철회·시간 초과 후 도착한 결과는 폐기한다. 작업이 소유한 임시 사진만 삭제하며 최신 요청의 사진을 삭제하지 않는다.
4. 분석 요청 시 프로필과 목표의 요약·설명·revision을 스냅샷으로 고정한다. 목표가 pending이면 비교 대상으로 쓸 수 없으므로 목표를 지정한 요청은 `409 GOAL_NOT_READY`다. 목표를 지정하지 않은 분석은 허용한다.
5. 목표 삭제 시 분석의 외래키는 null로 바꿀 수 있지만 완료된 비교 내용은 스냅샷으로 남는다. 화면은 “분석 당시 목표 기준”으로 표시한다.
6. 목표 사진 원본은 성공·실패·취소·시간 초과 모두 정리한다. 삭제 실패는 객체 키가 보존된 정리 작업으로 재시도한다.
7. 분석 화면은 2초 간격으로 최대 60초 자동 조회한다. 서버는 최대 90초 처리한다. 60초 후에는 기록 화면의 “처리 중”으로 전환하고 서버 실패로 단정하지 않는다. 앱 복귀·사용자 새로고침 시 상태를 다시 확인한다.
8. 일일 3회 분석 제한은 KST 당일 pending+done이며 접수와 횟수 예약을 원자적으로 처리한다. 실패·취소는 예약을 해제한다. 동시 pending 1개 제한도 같은 트랜잭션에서 적용한다. reset_at은 다음 KST 자정이다.

완료 결과나 사진을 삭제해도 이미 성공한 당일 사용 횟수는 돌려주지 않는다. 사용량 집계에 필요한 최소 상태 이력은 당일 제한을 유지할 수 있도록 관리한다.

## F-07: 루틴 선택과 날짜 관리

### 집중 부위와 종목 선택

1. 입력 분석은 사용자 소유의 done 분석이어야 한다. 목표는 필수가 아니다.
2. 우선 부위는 유효한 `goal_comparison.priority_parts`를 먼저 사용한다. 없으면 검증된 caution 판정의 매핑을 사용한다. 둘 다 없으면 현재 프로필의 목적·경력·횟수 기반 기본 균형 템플릿을 사용한다. “정상”, “평가 불가”, 글 분석도 기본 루틴을 생성할 수 있다.
3. caution→운동 부위 매핑과 목적별 템플릿은 서버 설정 데이터에 둔다. 검증되지 않은 판정에서 교정 효과를 단정하거나 임의의 부위를 만들지 않는다. 매핑이 없으면 기본 템플릿을 사용한다.
4. 제안 난이도 상한: under3m=2, under1y=3, over1y=5. 이는 팀 검토용 선택 정책이며 효과·안전성의 검증 결과가 아니다.
5. 세트는 종목의 min_sets~max_sets 안에서 경력별 처방 데이터를 사용한다. 횟수와 유효한 중량 범위도 같은 처방 데이터에서 선택한다. 맨몸 중량과 검증된 개인 중량 근거가 없는 기구 운동의 목표 중량은 null이다. 몸무게만으로 특정 중량을 만들어 넣지 않는다.
6. MVP의 기구 선택 입력은 추가하지 않는다. 기본 템플릿은 맨몸 종목으로도 실행 가능한 대안을 갖춘다. 사용자는 자유 운동을 선택할 수 있다. 기구 보유를 확인하지 않은 루틴의 설명에는 실행 환경 확인을 안내한다.
7. 활성 종목·난이도·처방 조건을 충족하는 후보가 부족하면 검증된 기본 템플릿으로 대체한다. 기본 템플릿도 구성할 수 없으면 `409 ROUTINE_DATA_NOT_READY`이며 기존 루틴은 유지한다. 빈 종목 루틴을 성공으로 저장하지 않는다.

### 향후 7일 생성·재생성

1. 생성 범위는 요청일 D부터 D+6까지 7일이다. 최초 생성에서 주당 횟수 f의 운동일 오프셋은 `floor(i*7/f)`, i=0..f-1이다. 예: f=3이면 0·2·4일. 모든 날짜를 운동일 또는 휴식일로 저장한다.
2. 운동 시작 기록이 한 번이라도 생성된 날짜는 `execution_locked=true`가 되어 루틴 종목·ID·처방을 교체하지 않는다. 이후 기록을 삭제해도 잠금은 유지한다. done·skipped 날짜도 유지한다.
3. 재생성 시 고정 운동일 수를 p라 하면 수정 가능한 날짜에 추가할 운동일은 `max(0,f-p)`다. 고정된 휴식일을 제외한 후보 날짜를 시간순으로 배열하고 같은 균등 배치 공식을 후보 개수에 적용한다. 후보 부족 시 가능한 날짜만 생성하고 `FREQUENCY_NOT_FULLY_SCHEDULED` 경고를 반환한다. 고정 운동일이 f를 초과하면 그대로 유지하고 `LOCKED_DAYS_EXCEED_FREQUENCY`를 반환한다.
4. 변경 가능한 날짜의 기존 planned 루틴만 트랜잭션 안에서 교체한다. 새 루틴 구성 실패 시 전체 교체를 롤백한다. 날짜별 운동 시작과 생성은 같은 사용자 잠금으로 직렬화한다.
5. 같은 분석으로 재요청할 수 있다. 현재 프로필에 따라 재생성하며, 잠긴 날짜는 보존한다. 분석 당시 프로필과 루틴 생성 당시 프로필은 각각 스냅샷으로 저장한다.
6. 주간 조회는 항상 월~일 7칸이다. 날짜 상태는 `ungenerated`, `rest`, `workout`이다. 미생성 날짜를 휴식일로 표시하지 않는다. 생성 범위 만료 시 홈에 “다음 루틴 생성”을 표시하고 기존 POST로 다음 7일을 생성한다. 자동 주간 갱신은 MVP에 추가하지 않는다.
7. 루틴 원문 상태 planned/done/skipped를 유지한다. 진행 중은 별도 `execution_locked`, `in_progress_count`, `done_count`로 표현한다. items[].done은 해당 루틴·종목의 completed 로그 중 완료 세트가 1개 이상 존재할 때 true다. 전 종목 true면 done, 그렇지 않으면 planned다. skipped는 사용자 명시 동작이며 시작 기록이 있는 루틴에는 허용하지 않는다.

## F-09·F-10·F-15·F-16: 운동·복원·통계

1. 사용자당 in_progress 로그는 최대 1개다. `(exercise_id,routine_id)`가 모두 같으면 200/resumed=true, 다르면 `409 WORKOUT_IN_PROGRESS`다. 자유 운동의 routine_id는 null로 비교한다. 기존 운동을 마치거나 취소한 뒤 새 운동을 시작한다.
2. 루틴 시작은 내 루틴의 당일 종목에만 허용한다. 미래·과거 날짜나 skipped 루틴은 `409 ROUTINE_NOT_STARTABLE`이다. 이미 완료한 종목은 `409 ROUTINE_ITEM_ALREADY_DONE`이며 반복 수행은 자유 운동으로 시작한다. 하루 루틴 안에 같은 exercise_id를 중복 배치하지 않는다.
3. 서버 started_at의 KST 날짜를 workout_date로 고정한다. 자정을 넘어도 시작일 기록이다. 앱 복원 조회는 현재 시각−6시간에 걸친 KST 날짜 구간으로 status=in_progress를 조회한다. 앱 시작·홈 진입 시 복원 여부를 확인한다.
4. started_at+6시간 이상이면 aborted로 전환한다. 입력·조회 시에도 만료를 확인해 배치 지연에 의한 유령 이어하기를 막는다. aborted는 기록 조회는 가능하지만 통계·연속 운동·미션 인정에서 제외한다.
5. 세트 추가는 client_set_id로 멱등 처리한다. 같은 ID·같은 내용은 기존 세트 반환, 다른 내용은 `409 IDEMPOTENCY_CONFLICT`다. 중복 세트 번호는 거절한다. 세트 삭제는 번호를 자동 재배치하지 않는다.
6. 세트 PATCH 성공은 version+1이며 최신 값을 반환한다. DELETE에도 마지막 version을 query로 보내고 충돌을 검사한다. 로그 종료와 세트 변경은 같은 로그 잠금 안에서 검증한다.
7. completed 로그의 세트 수정·추가는 허용한다. 완료 세트가 0개가 되는 수정·삭제는 `409 COMPLETED_LOG_REQUIRES_DONE_SET`이다. 그 경우 사용자가 운동 기록 전체 삭제를 선택할 수 있다. 완료 상태를 자동으로 in_progress로 되돌리지 않는다.
8. 세트 변경·로그 완료·로그 삭제는 완료 세트 수, 볼륨, 루틴 종목 완료, 하루 루틴 상태를 같은 트랜잭션에서 재계산한다. 삭제로 done 조건이 깨지면 planned로 돌아가며 잠금은 유지한다.
9. 종료에는 완료 세트 최소 1개가 필요하다. 같은 종료를 재호출하면 저장된 completed 로그를 200으로 반환하고 종료 시각·시간을 다시 계산하지 않는다. aborted 종료는 충돌이다.
10. duration은 서버 경과 시간 이하의 앱 값만 허용하고 값이 없으면 서버 경과 시간이다. 음수·미래 시각 기반 값은 거절한다. 휴식 타이머는 앱에 만료 시각을 저장하고 복원 시 남은 시간을 다시 계산한다.
11. 홈·통계·연속 운동은 같은 집계 기준을 쓴다: completed이고 완료 세트가 1개 이상인 로그만 포함. 볼륨은 완료 세트의 weight_kg×reps 합이다. 맨몸 중량 null은 볼륨에 0으로 기여하지만 운동일은 인정한다. 동일 날짜 여러 종목은 운동일 1일이다.
12. 과거 날짜 기록 삭제·수정 시 연속 기록도 다시 계산한다. 진행 중·중단 세트는 전체 조회에 보여도 완료 통계에는 포함하지 않는다.

## F-11: 탈퇴·사진 삭제

탈퇴 응답을 202로 바꾼다. 서버는 한 트랜잭션에서 계정 접근 차단, JWT 버전 증가, 정리 대상 객체 키가 포함된 영속 정리 작업을 등록한다. 등록 실패 시 탈퇴 접수도 롤백하고 503을 반환한다. 처리 성공 뒤 모든 인증 요청을 401로 거절한다. 외부 파일 삭제 완료를 기다리지 않고 접수 결과를 반환한다.

앱은 202 또는 회원 상태를 확인하는 요청의 401을 받은 뒤 로컬 토큰·개인 캐시·예약 알림을 지우고 로그인 화면으로 이동한다. 네트워크 응답 유실 시 화면에서 “처리 결과 확인 중”을 표시하고 GET /api/users/me로 확인한다. 401이면 세션을 정리하되 탈퇴의 물리 삭제 완료를 단정하지 않는다. 살아 있는 계정이면 재시도할 수 있다.

24시간은 정리 작업의 정상 처리 목표이며 재시도 종료 시점이 아니다. 실패 작업은 보존하고 운영자가 확인할 수 있게 한다. 정리 완료 전에 객체 키를 잃지 않는다. 개별·전체 사진 삭제도 접근 차단 후 같은 정리 방식으로 처리한다. 실제 파일 삭제 완료 전에 새 조회 URL을 발급하지 않는다. 이미 발급한 URL은 최대 1시간 남을 수 있으므로 즉시 물리 삭제 실패까지 즉시 접근 차단 완료라고 표시하지 않는다.

## F-18: 식단·알레르기

- 활동량 입력이 없는 MVP 프로필에서 활동량을 추정했다고 표현하지 않는다. 식단 계산 설정에 팀이 승인한 기본 활동 계수와 산식 버전을 명시하고 결과에 가정값을 표시한다.
- gender=none·지원되지 않는 연령 등 산식 적용 범위 밖에는 수치 식단을 생성하지 않고 `409 DIET_FORMULA_NOT_APPLICABLE`을 반환한다. 지원 범위와 계수는 실제 검증 자료 없이는 확정할 수 없는 출시 조건이다.
- 알레르기 변경마다 allergy_revision을 증가시킨다. 과거 식단이 최신 revision과 다르면 needs_regeneration으로 표시하고 식사 항목·추천은 숨긴다. 서버는 상세 조회에도 같은 규칙을 적용한다.
- 식단 생성 완료 시 요청 당시와 현재 allergy_revision을 비교한다. 달라졌으면 결과를 적용하지 않고 ALLERGY_CHANGED로 실패한다. 재생성 시 최신 알레르기를 반드시 입력에 포함한다.

## F-19: AI 대화·루틴 제안

대화는 최근 기록 기반 동기 응답 정책을 유지한다. client_request_id로 동일 질문 재전송을 구분한다. 사용자별 하루 성공 질문+진행 중 예약 합계로 30회를 검사하고, 실패 시 예약을 해제한다. 요청 ID 재사용 시 내용이 다르면 충돌이다. 저장된 동일 요청은 기존 응답을 반환하고 횟수를 다시 차감하지 않는다.

모든 제안은 routine_id·base_revision·변경 목록·생성/만료 시각을 저장한다. add만 있어도 대상 루틴이 정해진다. GET 대화 기록은 assistant 메시지에 연결된 제안을 현재 상태와 함께 반환한다. 만료된 제안도 기록으로 조회하되 승인 버튼은 비활성화한다.

승인 시 소유권, 24시간 만료, pending 상태, 루틴 revision, execution_locked=false를 확인한다. 실패는 루틴을 변경하지 않는다. 적용은 트랜잭션으로 처리하고 revision을 증가시킨다. 같은 결정을 재전송하면 기존 결과를 반환하며 반대 결정을 다시 보내면 충돌이다. 루틴을 빈 종목으로 만드는 제안·중복 종목·범위 밖 처방은 적용하지 않는다.

루틴 종목·처방 변경과 건너뛰기는 revision을 증가시킨다. 운동 시작은 execution_locked 검사로 제안 적용을 막으며, 단순 통계 조회로 revision을 올리지 않는다. 교체한 종목에 이전 종목의 중량을 자동 승계하지 않는다. AI 제안의 중량도 검증된 개인 처방 근거가 없으면 null이며 휴식 기본값은 기존 90초다.

## F-20·F-21·F-25: 커뮤니티와 신고 운영

댓글 편집은 2차에서 제외한다. 원문의 “댓글 수정” 표현을 “댓글 작성·삭제”로 바꾸어 현재 API와 맞춘다. 게시글 편집은 유지한다. 자신의 글·댓글 쓰기/수정/삭제에는 소유권을 검사한다. 다른 사용자의 공개 콘텐츠 읽기에는 개인 데이터 소유권 404 규칙을 적용하지 않는다.

차단 사용자·숨김·삭제 콘텐츠는 목록뿐 아니라 직접 상세·댓글 조회에서도 제외한다. 해당 대상은 사용자 API에서 404다. 기존 알림이나 URL로 숨김 콘텐츠에 우회 접근할 수 없어야 한다.

서로 다른 신고자 3명 이상인 유효 신고로 자동 숨김한다. 신고 중복은 같은 신고의 반환으로 처리한다. 유효 집계 대상은 pending 및 위반 인정 resolved이며 rejected는 제외한다. 신고 한 건을 rejected로 바꿔도 남은 유효 신고가 3명 이상이면 자동 복구하지 않는다. 관리자 별도 숨김은 신고 수 감소로 복구되지 않는다. 운영 조치·사유·처리자·시각을 기록한다.

기존 GET /api/admin/reports와 PATCH /api/admin/reports/{report_id}를 커뮤니티와 함께 2차에 배치한다. 전용 관리자 UI는 여전히 Swagger/Postman으로 대체 가능하다. 삭제 회원의 관리자 조회는 email·nickname을 null로 반환하고 deleted_at만 남기며 지워진 개인정보를 예시로 재노출하지 않는다.

## F-22·F-23·F-24: 확장 기능

### 제휴 상품

제휴 목록·상세는 활성 제휴사·활성 상품·유효 게시 기간을 모두 검사한다. 종료·비활성 상품 상세도 404다. 제휴 홍보 상품의 is_advertisement는 true로 고정하며 등록·수정에서 false를 거절한다. 일반 비광고 상품은 현재 기능 범위에 추가하지 않는다.

### 미션·할인권

별도 참여 API를 추가하지 않고 current 조회 시 활성 미션의 사용자 참여를 유일 키로 자동 생성한다. 참여일보다 이전 기록은 인정하지 않는다. GET의 참여 생성 효과를 API에 명시하고 중복 조회로 참여를 늘리지 않는다.

운동일 미션의 기본안은 참여일 이후 미션 기간 내 KST 날짜별 completed 로그 duration 합계가 600초 이상인 날을 1일로 인정하는 것이다. 같은 날짜 4종목은 1일이며 aborted·in_progress는 제외한다. 미션에는 목표 일수·시작/종료일·발급 가능한 쿠폰 수량을 필수로 저장한다. 기록 삭제 전의 인증된 미션 인정 이벤트를 보존한다. 보상 지급 후 사용자가 운동 기록을 삭제해도 지급 이력을 취소하지 않는다. 지급 전 삭제는 재계산한다.

사용자·미션당 보상 1회, 쿠폰 코드당 발급 1회를 트랜잭션과 유일 키로 보장한다. 외부 쿠폰 코드 공급은 운영자가 미리 등록한 코드 풀을 사용한다. 응답에는 code·expires_at·redemption_url·redemption_instructions를 포함한다. 앱은 발급·조회만 하고 실제 사용 확인은 제휴사에서 한다. 사용 이력이 연동되지 않으면 used_at은 null이며 자체적으로 “사용 완료”라고 표시하지 않는다. 코드 공급·사용처가 준비되지 않으면 미션을 활성화하지 않는다.

### 푸시

확장에 DELETE /api/users/me/device-token?platform=ios|android를 추가한다. 앱 로그아웃은 토큰 해제 요청을 먼저 시도하고, 실패해도 로컬 로그아웃은 수행한다. 토큰 해제 실패 가능성을 고려해 푸시에 사진·분석 내용 등 개인 상세를 넣지 않고 딥링크는 인증 후 조회한다.

같은 FCM 토큰은 한 계정만 소유한다. 새 계정 등록 시 이전 연결을 원자적으로 해제한다. 플랫폼별 1기기 정책은 유지하며 갱신은 이전 토큰을 대체한다. 탈퇴는 모든 토큰을 삭제한다. 알림 발송 직전 동의·설정·계정 상태·현재 토큰을 확인한다. KST 날짜·유형별 발송 키로 중복을 막는다.

공지 고정 여부 is_pinned는 MVP/2차 관리 API에 추가하지 않고 초기 데이터·운영 설정으로 관리한다. API 응답 필드가 사용자 수정 가능 필드라는 의미는 아니다.
