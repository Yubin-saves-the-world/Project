# 앱(프론트) 개발 계획 — 팀원용

작성: 2026-10-25 · 대상: 앱 담당 팀원 · 같이 보는 문서: `프론트_MVP_페이지별_작업명세.md`(페이지별 API 상세), `design/settings/`(설정 화면 디자인), `FE_AGENTS.md`(코덱스용 지시서)

## 1. 한 줄 요약

서버(백엔드)는 MVP를 **모두 만들어 두었습니다.** 앱은 가입·로그인·신체정보까지만 서버와 연결되어 있고, 나머지는 **화면을 만들고 서버를 연결하는 일**이 남았습니다. 아래 작업 14개(T0~T13)를 순서대로 하면 MVP가 끝납니다.

## 2. MVP 범위

### 목표 (이 한 바퀴가 앱에서 끝까지 돌면 완료)

가입 → 신체정보 → 사진 올리고 분석 결과 보기 → 목표 체형 등록 → 오늘의 루틴 확인 → 운동하며 세트 기록·종료 → 기록 보기

### 포함 / 제외

| 포함 (MVP) | 제외 (지금은 "준비 중"으로 둠) |
|---|---|
| 가입·로그인·로그아웃·탈퇴 | AI 코치 탭, 커뮤니티 탭 |
| 신체정보 입력·수정 | 식단, 알레르기 |
| 사진 올리기·관리 | 운동 통계 화면, 연속 운동일 화면 |
| 체형 분석(진행·결과·기록) | 글로 하는 체형 분석, 자세 교정 운동 |
| 목표 체형 | 제휴 상품, 미션, 할인권 |
| 맞춤 루틴(생성·주간·상세) | 푸시 알림, 알림 설정 |
| 운동 종목, 운동 진행(세트·휴식 타이머), 운동 종료 | 구글·카카오 로그인 |
| 운동 기록(달력·목록·상세·수정·삭제) | 비밀번호 변경(서버에 API 없음), 프로필 사진 |
| 설정(내 정보, 사진 관리, 동의 관리) | 관리자 기능 |

비밀번호 찾기는 이미 서버와 앱 모두 연결되어 있으니 그대로 둡니다.

## 3. 지금 어디까지 되어 있나

> **먼저 확인:** 이메일 인증 연결과 비밀번호 찾기 수정(인증번호 방식)은 백엔드 담당 PC의 `main`에는 들어가 있지만 **아직 GitHub에 올라가지 않았습니다.** GitHub 버전만 보면 앱은 개발용 인증번호와 메일 링크 방식의 비밀번호 찾기를 쓰고 있는 것으로 보입니다. 올리기 전까지는 아래 "서버 연결됨"이 GitHub 코드에는 해당하지 않습니다. (7장 대응표 참고)

| 영역 | 상태 |
|---|---|
| 회원가입(이메일 인증), 로그인, 비밀번호 찾기 | 서버 연결됨 |
| 신체정보 입력 | 서버 연결됨 |
| 동의 화면 | 화면만 있음. 서버 연결 확인 필요 |
| 사진 분석 입력 화면 | 화면만 있음. 서버 호출 없음 |
| 홈, 운동 달력 | **수동 일정(요일별 운동·휴식, 매주 반복)·로컬 운동 기록·달력이 이미 동작.** 서버 연결만 없음 (기존 기능은 보존하고 서버를 덧붙임) |
| 운동 기록 화면 | 빈 화면 |
| 목표 체형, 종목, 루틴, 운동 진행, 설정 | 화면 없음 |

**서버 주의:** 체형 분석·목표 체형의 AI는 아직 **가짜 응답**입니다. 사진과 상관없는 값이 나옵니다. 화면은 실제와 똑같은 모양이므로 그대로 만들면 됩니다. (응답의 `measurement_version`이 `stub-v0`이면 가짜입니다.)

## 5. 작업별 완료 기준 (이게 되면 끝)

| # | 완료 기준 |
|---|---|
| T0 | 기존 가입·로그인이 그대로 동작. 토큰이 만료되면 어느 화면에서든 로그인 화면으로 이동 |
| T1 | 앱을 껐다 켜도 로그인이 유지됨. 동의가 없는 계정은 동의 화면, 신체정보가 없으면 입력 화면, 그 외 홈으로 이동. 가입에 실제 인증번호(서버)가 쓰이고 `email_verification_token`이 전달됨. 비밀번호 찾기가 인증번호 방식. **로그인 실패(401)는 로그아웃으로 처리하지 않고 입력 오류로 표시** |
| T2 | 설정에서 신체정보 수정 가능. 목표·횟수·경력을 바꾸면 "루틴을 새로 만들까요?" 안내 |
| T3 | 사진 올리기 성공. 촬영 방향이 돌아가지 않음. 20장이 넘거나 10MB가 넘으면 안내. 삭제 가능 |
| T4 | 정면(필수)·측면(선택) 사진으로 분석 요청 → 진행 화면 → 결과. 분석 실패(흐림·전신 아님 등)와 값 없음(측정 못 함)이 각각 안내됨. 하루 3회 한도 안내 |
| T5 | 설명만으로 바로 등록, 사진으로 등록하면 처리 중 표시 후 완료. 수정·삭제 가능 |
| T6 | 부위·기구 필터와 이름 검색이 동작. 종목을 고르면 자유 운동으로 시작 |
| T7 | 분석 결과 화면의 버튼으로 루틴 생성. 쉬는 날이 있는 주간 화면, 루틴 상세, 종목별 시작 버튼 |
| T8 | 기존 홈 테스트가 그대로 통과. 서버 루틴이 있으면 오늘의 종목으로 표시, 진행률·운동한 날·오늘 볼륨이 서버 값으로 나옴. 진행 중인 운동이 있으면 "이어하기". 수동 일정에서 휴식일로 바꾸면 해당 날의 서버 루틴을 건너뜀 처리 |
| T9 | 세트 추가·수정·삭제, 휴식 타이머, 앱을 껐다 켜도 진행 중이던 운동이 복원. 네트워크가 끊겼다 돌아와도 세트가 중복으로 쌓이지 않음 |
| T10 | 종료하면 시간·볼륨·세트 수·루틴 진행(3/4)이 보임. 완료 세트가 0개면 기록을 지우고 안내 |
| T11 | 월 달력에서 운동한 날 표시, 날짜별 목록·상세, 세트 수정·기록 삭제 후 홈과 일치 |
| T12 | 디자인과 동일한 설정 화면. 작은 화면(폭 320)과 큰 글씨(130%)에서 글자가 잘리거나 넘치지 않음. 탈퇴는 확인 체크 후에만 가능 |
| T13 | 새 계정으로 "가입 → … → 기록 보기" 한 바퀴가 끝까지 돌아감. 실패하는 단계가 없음 |

## 6. 코덱스로 개발하는 방법

1. `FE_AGENTS.md`를 앱 폴더(`FE/`)에 `AGENTS.md`라는 이름으로 복사합니다. 코덱스가 자동으로 읽습니다.
2. **작업 하나씩** 시킵니다. 예시:
   - `AGENTS.md를 읽고 T3(사진 올리기·관리)만 진행해 줘.`
   - `T4를 진행해 줘. 분석 진행 화면의 폴링 부분부터 시작해 줘.`
3. 코덱스가 끝나면 마지막 보고에 **바꾼 파일, 추가한 테스트, 분석·테스트 결과**가 나옵니다. 이 내용을 확인한 뒤 직접 앱을 실행해 눈으로 확인합니다.
4. 한 번에 여러 작업을 시키지 마세요. 앞 작업의 결과가 뒤 작업의 입력이 되므로 한 번에 시키면 서로 어긋납니다.
5. 코덱스가 모르는 것은 추측하지 않고 물어보게 되어 있습니다. 서버 응답이 이상하면 코드를 고치기 전에 백엔드 담당(이지한)에게 먼저 물어보세요.

### 코덱스에게 알려 둔 중요한 규칙 (팀도 알아야 함)
- 팀의 설계 문서(`docs/frontend-architecture`)는 Riverpod·Dio를 제안하지만 **실제 코드는 ChangeNotifier + http** 입니다. 코덱스는 **지금 있는 코드의 방식**을 따르도록 되어 있습니다. 방식을 바꾸고 싶으면 팀에서 먼저 정하고 `FE_AGENTS.md`를 고치세요.
- 화면 이미지 비교 테스트는 Flutter 버전에 따라 결과가 달라집니다(새 버전에서 약 14개가 어긋난 적이 있고, 다른 환경에서는 모두 통과한 기록도 있음). 코덱스는 시작 전에 **현재 실패 목록과 Flutter 버전을 기록**하고, 기준 이미지를 임의로 갱신하지 않으며, "새 실패가 없는지"만 봅니다. 팀 공통 버전은 결정 D4입니다.
- 코덱스는 **기존 앱 디자인과 기존 기능(수동 일정 등)을 보존**하도록 되어 있습니다. 색·테두리는 앱의 `AppColors`를 따르고, 디자인 파일의 색 값은 참고용입니다.
- 로그인 실패(401)는 입력 오류이고, 로그인 이후 요청에서 온 401만 "세션 만료 → 로그인 화면"으로 처리합니다.
- 코덱스는 `git commit`을 하지 않습니다. 확인한 뒤 직접 커밋하세요.

## 7. 서버 테스트하는 법

- 앱은 `--dart-define=API_BASE_URL=서버주소`로 서버를 지정합니다.
  - iOS 시뮬레이터: `http://localhost:8080`
  - 안드로이드 에뮬레이터: `http://10.0.2.2:8080`
- 서버는 **백엔드 담당(이지한)** 이 켭니다. 필요할 때 요청하세요. 서버가 켜져 있으면 Swagger 화면에서 모든 API를 직접 눌러 볼 수 있습니다.
- 인증번호는 개발 서버에서는 **메일이 아니라 서버 로그**에 찍힙니다. 가입을 시연할 때는 백엔드 담당이 로그를 보여 줘야 합니다.
- 서버 AI는 가짜 응답이고, 사진 분석은 하루 3회 한도가 있으니 테스트 계정을 여러 개 쓰세요.

## 8. 자주 하는 실수 (앱에서 특히 조심)

1. 업로드 전에 **사진의 촬영 방향(회전)을 반영하지 않음** → 분석이 계속 실패합니다.
2. 분석 `failed`를 통신 오류로 처리 → 실패해도 서버는 정상 응답(200)을 줍니다. 상태 값을 보세요.
3. 분석 결과의 값이 없을 때(`null`) 0으로 표시 → "측정하지 못했어요"로 보여 주세요.
4. 세트를 다시 보낼 때 **새 번호를 만듦** → 같은 세트가 두 번 쌓입니다. 한 번 만든 `client_set_id`를 계속 쓰세요.
5. 운동 경과 시간을 앱 타이머로만 셈 → 앱을 나갔다 오면 어긋납니다. 서버가 준 `started_at` 기준으로 계산하세요.
6. 분석이 끝나면 루틴이 자동 생성될 것으로 기대 → 버튼을 눌러 앱이 루틴 생성을 요청해야 합니다.
7. 운동 기록 조회 기간이 92일을 넘음 → 오류가 납니다. 달력은 월 단위로 요청하세요.
8. 로그인 만료(401)를 화면마다 따로 처리 → 한 곳에서 처리합니다(T0).

| **D1-a** 직접 고른 운동이 있는 날에 추천 루틴이 생기면 | **제안:** 사용자가 **둘 중 하나를 선택**합니다(합치거나 추가하지 않음). 기본은 "내 운동 유지"(그날 서버 루틴은 건너뜀 처리), 선택하면 "추천 루틴으로 바꾸기"(직접 고른 운동은 지워진다고 확인 창 안내) | T7, T8 |

| **D1** 수동 일정 vs 서버 추천 루틴 | 앱에는 요일별 운동·휴식·매주 반복이 이미 있는데 서버에는 이를 저장하는 API가 없습니다. **제안:** 수동 일정은 앱(로컬)이 그대로 관리하고, 서버 루틴은 "그날 할 종목"을 주는 선택 기능으로 둡니다. 휴식일로 바꾸면 서버 루틴을 건너뜀 처리합니다(서버에 이미 있는 API). 기기 간 동기화가 필요하면 서버 API를 새로 만들어야 합니다. **(서버 변경 완료: `PATCH /routines/{id}`가 `skipped`·`planned` 둘 다 받음. 되돌리기는 오늘 이후 날짜만)** | T7, T8 |
| **D3** 탈퇴 시 작성한 글·댓글 | 지금 서버는 **함께 삭제**합니다. "탈퇴한 사용자"로 남기려면 서버를 바꿔야 합니다. MVP에는 커뮤니티 화면이 없어서 급하지 않습니다 | 탈퇴 안내 문구(T12) |
| **D2** 개인정보 처리방침 링크 | 아직 주소가 없습니다. **앱 담당 요청: 설정 화면(T12)을 마무리하기 전까지 필요**(그전에는 해당 행을 비활성으로 둠). 팀장이 주소를 정해야 합니다 | 설정 화면(T12) |
| **D4** 팀 Flutter 버전 | **Flutter 3.41.6 / Dart 3.11.4로 제안 (앱 담당 환경에서 전체 테스트 통과, `pubspec.yaml`의 최소 Dart `^3.11.4`와 일치). 팀장 확인 대기.** 확인되면 이 버전을 기준으로 이미지 비교 테스트의 실패 목록과 원인을 확인하고, 기준 이미지는 임의로 갱신하지 않습니다 | 테스트 신뢰도 |

## 9-2. 앱 코드 점검 결과에 대한 대응

앱 담당이 현재 앱 코드와 이 문서를 비교해 올려 준 7가지에 대한 처리입니다.

| 3 | 비밀번호 찾기가 메일 링크 방식 | 같은 원인. 서버는 인증번호 방식(`reset-request` → `reset-verification` → `reset`)이고 계약을 지시서에 적음. 앱 수정본은 이미 로컬 `main`에 있음 |
| 4 | 자료를 못 찾음(`openapi.yaml`, 작업 명세, 설정 디자인) | 팀 저장소에 없고 백엔드 담당 PC 폴더에만 있었음. `FE전달용/` 폴더(와 zip)로 묶어 전달 |

### 9-3. 수정 코드 적용 방법 (앱 담당용)

`FE전달용/수정코드/`에 두 가지가 있습니다.
1. `fe_이메일인증_비밀번호찾기.patch` — 이메일 인증 연결, 비밀번호 찾기(인증번호 방식) 수정, 관련 테스트. **원격 `main` 기준으로 충돌 없이 적용되는 것을 확인했습니다.**
2. `server_auth_flow_test.dart` — 원격에서 이 파일의 코드 정렬을 새로 해 두어서 패치로는 충돌합니다. 이 파일만 통째로 교체하고 `dart format`을 한 번 돌리세요.

```bash
git checkout main && git pull
git apply --check 수정코드/fe_이메일인증_비밀번호찾기.patch   # 검사
git apply 수정코드/fe_이메일인증_비밀번호찾기.patch
cp 수정코드/server_auth_flow_test.dart FE/integration_test/server_auth_flow_test.dart
dart format FE/integration_test/server_auth_flow_test.dart
```

팀장이 GitHub에 올리면 위 작업은 필요 없습니다. 올린 뒤에는 이 패치를 쓰지 마세요(중복 적용됨).

**Flutter 버전 고정 방법(D4, 3.41.6 / Dart 3.11.4 기준):** 팀 전원이 같은 버전을 쓰도록 `FE/README.md`에 버전을 적고, FVM을 쓰면 `FE/.fvmrc`에 `{"flutter": "3.41.6"}`를 넣습니다. 버전이 다른 환경에서 이미지 비교 기준을 갱신하지 마세요.
