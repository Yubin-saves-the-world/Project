# MOVID 전체 프론트 기능·연동 검토

> 아래는 수정 전 검토 기록이다. 이후 반영한 수정과 재검증은 [후속 수정 보고서](INTEGRATION_REVIEW_FIXES_2026-10-28.md)를 참고한다.

검토일: 2026-10-28. 대상: `/Users/yubin/StudioProjects/Project/FE`.

## 결론

주요 화면과 서버 API 호출 경로는 대부분 구현되어 있다. 그러나 **화면이 구현된 것과 실제 서버에서 전체 흐름이 검증된 것은 다르다.** 현재 빌드 설정은 로컬 미리보기이며, 수동 일정의 운동 기록과 서버 운동 기록도 분리되어 있다. 따라서 아직 모든 화면의 데이터가 하나의 서버 기준으로 통일됐다고 볼 수 없다.

이번 검토에서는 앱 코드·디자인·저장 데이터를 수정하지 않았다. 기존 앱 아이콘·시작 화면 작업과 미추적 파일을 보존했다. 이 보고서와 인수인계 링크만 추가하며 커밋·Push하지 않았다.

## 검토 기준과 검증 범위

- 현재 FE: `2b42b4f` 및 작업 폴더의 미커밋 변경 포함. `lib`의 Dart 소스는 152개다.
- 최종 요구사항 v0.3과 이후 사용자가 확정한 변경, 인수인계 문서, 현재 화면·ViewModel·Repository·공통 API 코드를 비교했다. 옛 기획의 자동 일정 배정을 최신 수동 주간 일정 정책보다 우선하지 않았다.
- 최신 API 계약: `docs/team-handoff/2026-10-25/api/openapi.yaml`.
- 백엔드 비교: 현재 main의 BE와, 로컬에 있는 `origin/feat/be-mvp-features`의 `ff6b9791e6c6a22dd1a7033eb67059ec356f9120` 소스. 후자는 임시 경로에 읽기용으로 추출했고 브랜치를 바꾸거나 서버를 실행하지 않았다. 이것이 현재 배포 서버 버전이라는 뜻은 아니다.
- 현재 iOS `Generated.xcconfig`의 `USE_LOCAL_PREVIEW=true`를 확인했다. 코드 기본값은 false이므로 옵션 없이 새 실행하면 서버 모드가 된다.
- 기본 주소 `http://localhost:8080/actuator/health`는 점검 당시 연결되지 않았다(HTTP 000, curl 종료 코드 7). 별도의 실제 테스트 서버 주소는 지정되지 않았다. 이 결과로 원격 서버까지 꺼져 있다고 단정하지 않는다.
- 이번 검토는 소스 흐름 추적·API 계약 비교·자동 테스트다. 모든 페이지를 기기에서 새로 조작하거나 최신 Figma와 전수 시각 비교한 결과는 아니다.

## 먼저 조정할 부분

### 1. 닉네임 저장 실패 후 같은 편집 화면에서 재시도가 막힘 — 확인된 기능 문제

**상황:** 마이페이지 → 프로필 편집 → 닉네임 저장 중 네트워크 오류 → 연결 복구 → 같은 화면에서 다시 저장.

`AccountSettingsViewModel`은 저장 결과가 불확실할 때 `needsReload=true`로 설정하고, 이후 `rename()` 호출을 막는다. 서버에 이미 반영됐을 가능성이 있으므로 재조회 자체는 필요한 보호 장치다. 문제는 프로필 편집 화면의 저장 콜백이 상태 재조회로 이어지지 않는다는 것이다. 버튼은 다시 누를 수 있지만 새 저장 요청은 전송되지 않는다. 편집을 닫고 다시 열면 재조회되어 회복된다.

- 근거: [저장 차단 조건](../../lib/features/settings/presentation/account_settings_view_model.dart#L17), [오류 후 needsReload](../../lib/features/settings/presentation/account_settings_view_model.dart#L80), [편집 진입 시에만 재조회](../../lib/features/profile/presentation/pages/my_page.dart#L102), [저장 콜백](../../lib/features/profile/presentation/pages/my_page.dart#L123).
- 영향: 서버 모드의 프로필 편집. 닉네임 중복 오류는 별도로 처리하므로 이 문제와 다르다.
- 권장: 초안을 유지하면서 서버의 현재 이름을 다시 확인하는 복구 동작을 제공하고, 확인 후 저장을 재개한다. 결과가 불확실한 PATCH를 곧바로 자동 반복하지 않는다.
- 검증: 임시 테스트에서 첫 실패 후 두 번째 저장 요청 수가 증가하지 않고, `load()` 이후에만 저장되는 것을 재현했다.

### 2. 목표 체형의 기존 설명을 지우는 의미가 UI·API 사이에서 정해져 있지 않음 — 확인된 불일치

**상황:** 설명이 있는 목표 체형을 편집하면서 설명을 모두 지우고 새 사진을 선택해 저장한다.

화면은 빈 설명을 `null`로 바꾸고, 서버 Repository는 null 필드를 요청에서 제외한다. 백엔드는 제외된 설명을 ‘기존 값 유지’로 처리하므로 지운 설명이 다시 나타난다. 사진을 바꾸지 않고 설명만 비우면 화면 검증에서 막힌다.

- 근거: [빈 설명을 null로 변환](../../lib/features/goal_body/presentation/goal_view_model.dart#L245), [null 필드 제외](../../lib/features/goal_body/data/server_goal_repository.dart#L21).
- 백엔드 근거: `BE/.../body/service/GoalBodyService.java`의 `update()`는 description이 null이면 유지한다. `body/dto/GoalPatch.java`와 OpenAPI는 설명에 최소 길이 1을 요구한다.
- **단순히 빈 문자열을 보내는 수정으로 해결하면 안 된다.** 현재 계약에서는 빈 문자열도 길이 검증 대상이다.
- 권장: 설명 삭제를 지원할지 먼저 정한다. 지원한다면 백엔드와 명시적 삭제 표현을 합의한다. 당장 계약을 유지한다면 화면에서도 ‘비우면 삭제’로 오해되지 않게 처리한다.
- 테스트 보완: `FakeGoalRepository.update()`는 description이 null일 때 기존 값을 유지하지 않아 실제 백엔드와 의미가 다르다. 이 때문에 가짜 저장소만 사용한 테스트로는 이 차이가 드러나지 않을 수 있다.
- 검증: 임시 요청 테스트에서 새 photo_id만 전송되고 기존 설명이 유지되는 것을 확인했다. 실제 HTTP 서버를 사용한 재현은 아니다.

### 3. 직접 만든 일정의 운동과 서버 운동의 저장·통계가 분리됨 — 기존 정책에 따른 연동 공백

| 시작 경로 | 저장 위치 | 서버 기록·통계 반영 |
|---|---|---|
| 직접 만든 주간 일정에서 운동 시작 | 기기의 Home 저장소 | 반영되지 않음 |
| 서버 추천 루틴에서 운동 시작 | 서버 workout-logs·sets | 서버 응답 기준 반영 |
| 서버 운동 목록에서 자유 운동 시작 | 서버 workout-logs·sets | 서버 응답 기준 반영 |

홈의 수동 운동은 서버 모드에서도 `_WorkoutPreviewForm`을 사용하며 ‘이 운동 기록은 현재 기기에 저장돼요’를 표시한다. 반면 서버 모드의 홈 연속 운동·주간 운동 일수는 서버 요약을 사용한다. 따라서 수동 운동을 완료해도 서버 통계가 올라가지 않는 상황이 발생한다. 기기 달력과 서버 기록 화면도 같은 기록을 보여주는 화면이 아니다.

- 근거: [수동 운동 실행·기기 저장 안내](../../lib/features/home/presentation/pages/home_page.dart#L305), [서버 운동 일수 우선 사용](../../lib/features/home/presentation/pages/home_page.dart#L848).
- 이는 기존 수동 일정과 기록을 보존하기 위해 이미 문서화한 분리다. 이번 검토에서 새로 발생한 회귀 오류로 보지는 않는다.
- 일정 종목은 고정 카탈로그의 인덱스를 저장하며 서버 exercise_id가 아니다. 종목 보기 화면을 서버에 연결했다고 수동 일정까지 자동으로 서버 ID로 바뀌지는 않는다.
- 권장: 최종 사용 경험을 통일하려면 새 일정 선택부터 서버 종목 ID를 사용하고 공통 서버 운동 실행 화면에 연결한다. 기존 인덱스와 기기 기록은 변환·보존 정책을 정한 후 처리한다. 이름이 비슷하다는 이유만으로 ID를 추측하여 이관하면 안 된다.
- 관련 기존 기록: `HOME_SERVER_INTEGRATION.md`, `WORKOUT_PROGRESS_INTEGRATION.md`.

### 4. 액세스 토큰 저장 방식 — 실서비스 전 보완 권장

현재 `PreferencesTokenStore`는 JWT를 일반 SharedPreferences 문자열로 보관하고 `ApiClient`가 기본 저장소로 사용한다. OS의 자격 증명 전용 저장소를 사용하는 구현은 없다.

- 근거: [현재 토큰 저장소](../../lib/features/auth/data/token_store.dart), [기본 저장소 선택](../../lib/core/network/api_client.dart#L32).
- 권장: 실제 배포 전 Keychain/Keystore를 이용하는 저장소로 교체하고 기존 토큰 이전·로그아웃 삭제·실패 처리를 검증한다. 일반 환경설정과 인증 자격 증명의 보관 기준을 구분할 필요가 있다.
- 현재 토큰 값을 읽거나 출력하지 않았으며, 이번 검토로 토큰 유출이 발생했다고 판단한 것은 아니다.

## 문서·프론트·백엔드 일치 여부

### 주요 계약은 코드에 반영되어 있음

- 공통 `/api` 경로, Bearer 토큰, snake_case JSON, 오류 코드·필드 오류, multipart 요청 구분.
- 가입 이메일 인증, 비밀번호 찾기 인증번호 확인, 내 정보·프로필, 사진·목표 체형·분석, 루틴·운동 로그·세트, 커뮤니티·신고·차단의 주요 요청 경로.
- 분석 pending/done/failed 상태와 루틴 생성, 운동 요청 식별자와 버전 충돌 처리.
- 사용자 정책상 ‘미선택’ 성별을 UI에서 제거했어도 레거시 파싱 호환용 enum이 남은 것은 오류가 아니다.

### 서버 설정과 브랜치를 맞춰야 함

현재 체크아웃의 BE main만 실행하면 최신 MVP의 모든 API가 있다고 가정할 수 없다. 추가 기능은 비교한 별도 브랜치에 있다. 실제 테스트 전에 팀이 제공하는 서버의 주소·구현 버전·메일/AI 동작 범위를 확정해야 한다. 여기서 BE 병합이나 배포를 수행하지 않았다.

`AppConfig` 기본 주소는 localhost다. 같은 Mac의 iOS 시뮬레이터, Android 에뮬레이터, 실제 휴대폰은 호스트에 접근하는 주소 조건이 다르므로 실행 기기에 맞는 `API_BASE_URL`이 필요하다. 현재 로컬 미리보기를 실제 서버 연결 성공으로 설명하면 안 된다.

### 계약에 따른 차이로, 새 버그로 판단하지 않은 항목

- 목표 사진은 서버에서 특징을 추출한 뒤 원본을 보관하지 않는 계약이다. 서버 처리 완료 후 사진 대신 요약을 보여주는 것은 이 정책과 일치한다. 영구 목표 사진 조회 기능이 누락됐다고 단정하지 않았다.
- 프로필 아바타 서버 업로드 계약은 없다. 기기에 저장한 내 아바타의 앱 내 공통 반영과 다른 기기까지 동기화하는 기능은 다르다.
- 서버 로그아웃은 현재 토큰을 클라이언트에서 폐기하는 구조다. API 호출을 안 했다는 이유만으로 로그아웃 불능이라고 판단하지 않았다.
- 기기별 수동 일정·이전 기록을 보존하는 동작과 새 서버 기록의 연동 공백은 구분해야 한다.
- 준비 중으로 정한 소셜 로그인·글 분석·AI 코치 등을 ‘버튼을 누르면 실제 기능이 완료된다’고 안내해서는 안 된다. 현재 준비 중 상태 자체는 확정된 범위에 따른 제한이다.
- 인수인계 README는 날짜별 누적 기록이다. 초기 절의 옛 비밀번호 찾기 설명보다 이후 갱신 항목과 현재 Repository를 우선해 확인했다. 다음 문서 정리 시 현재 상태 요약을 상단에 모으면 혼동을 줄일 수 있다.

## 권장 진행 순서

1. 프론트에서 닉네임 편집 실패 후 상태 확인·재시도 경로를 보완한다.
2. 목표 설명 삭제 규칙을 정한다. 현재 계약에서 빈 문자열 전송만 추가하는 방식은 피한다.
3. 수동 일정의 운동도 서버 기록·통계에 포함할 것인지 확정하고, 포함한다면 서버 종목 ID와 공통 운동 실행 화면으로 연결한다. 기존 데이터는 보존한다.
4. 실서비스 전에 토큰 저장소를 보완한다.
5. 최신 API를 제공하는 테스트 서버에서 가입·메일·비밀번호 변경 → 신체정보 → 분석·루틴 생성 → 운동·통계 → 프로필·동의·탈퇴 → 커뮤니티까지 실제 왕복 테스트를 한다. 이후 준비 중 기능을 별도 우선순위로 개발한다.

위 순서는 검토 제안이다. 이번 요청은 분석·검토이므로 기능 수정이나 서버 변경은 실행하지 않았다.
