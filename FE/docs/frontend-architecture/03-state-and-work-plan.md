# 상태 관리·데이터 흐름·구현 순서

이 문서는 프론트의 책임만 설명한다. 날짜별 루틴 생성 규칙·완료 판정·AI 작업 유효성·할당량·미션 보상·삭제 재시도는 서버 책임이다. 프론트는 해당 상태를 표시하고 사용자 입력을 보낸다.

## 1. 상태의 소유자

| 상태 | 소유 위치 | 수명·역할 |
| --- | --- | --- |
| 로그인·User·동의·온보딩 | auth/session_view_model | 앱 전체, 시작 시 GET me로 확인 |
| 토큰 | core/storage/token_store | 세션과 분리한 영속 저장 |
| 입력 중 가입·프로필 값 | 각 폼 ViewModel | 뒤로 이동 시 유지 범위를 지정, 비밀번호는 영속 저장하지 않음 |
| 정면/측면/목표 사진 초안 | photos 업로드 VM + 분석 입력 state | 업로드 결과 photo_id와 로컬 파일을 구분 |
| 분석 pending/done/failed | body_analysis Repository·진행 VM | analysis_id로 복원, 화면 이탈·복귀와 폴링 관리 |
| 목표 pending/done/failed | goal_body Repository·VM | 분석 요청보다 먼저 목표 done 확인 |
| 주간·오늘·루틴 상세 | routines Repository·관련 Provider | 날짜·루틴 ID별 동일 데이터 소유 |
| 실행 중 운동·세트·저장 상태 | workout Repository·실행 VM | 페이지 이탈로 서버 기록을 끝내지 않음 |
| 휴식 만료 시각·미전송 세트 | workout/local | 앱 종료 후 복원 가능한 영속 값 |
| 날짜 이력·집계 | workout Repository | 서버 집계가 기준, 수정 후 재조회 |
| 홈 카드 조합 | home_view_model | 다른 기능의 읽기 상태를 조합, 서버 모델 복제 없음 |
| 알레르기·식단 | diet Repository | 변경 시 기존 식단 무효 상태 반영 |
| AI 대화·제안 | ai_coach Repository | message_id/suggestion_id 기준, 상태는 서버 최신값 |

페이지가 서로의 ViewModel을 직접 생성하거나 호출하지 않는다. 다른 기능과 공유할 데이터는 공개 Repository/Provider를 통해 읽는다. app의 DI 구성은 모든 기능을 연결할 수 있지만 core와 ui/core는 features를 import하지 않는다. 기능의 전용 페이지는 다른 기능에서 가져와 중첩하기보다 라우터로 이동한다. photos의 공개 입력 위젯처럼 명시적으로 공유한 UI만 예외다.

## 2. 비동기 화면 설계

읽기 상태는 loading/data/error로, 변경 상태는 idle/submitting/success/error로 나눈다. 분석의 pending/done/failed는 서버 도메인 상태로 유지한다. 네트워크 error가 분석 failed와 같은 의미가 아니다. 기존 데이터 새로고침 실패 시 이전 값은 보존하고 오류 표시만 추가한다.

Notifier/AsyncNotifier는 상태와 행동을 관리하며 HTTP 접근은 주입한 Repository에 맡긴다. POST·PATCH·DELETE를 화면 build나 조회 Provider 초기화에 넣지 않는다. 버튼 이벤트에서 실행하고 처리 중에는 버튼을 잠근다. 상태 관리 도구의 자동 재시도나 HTTP 재시도 정책을 무조건 쓰기 요청에 적용하지 않는다. 재전송은 명시적 식별자와 서버 계약이 있는 경우에만 수행한다.

DTO 키는 서버의 snake_case를 모델의 camelCase에 매핑한다. null은 실제 결측값이며 `value ?? 0`으로 통계·수치·점수를 채우지 않는다. 지원하지 않는 enum은 unknown으로 읽고 잘못된 판단 대신 보수적인 화면을 표시한다. 새로 나온 오류 코드는 원문의 안전한 사용자 메시지 또는 일반 오류로 표시한다.

## 3. 주요 데이터 흐름

### 가입·로그인·설정

가입 요청 → 201 → 로그인 요청 → 토큰 저장 → GET me → 필수 동의/설문/홈 분기. 가입 성공 후 로그인 실패는 가입 폼 재제출로 처리하지 않는다. 이때 로그인 화면으로 이동하여 중복 계정을 만들지 않는다.

401은 auth_interceptor가 한 번 세션 만료를 통보하고 SessionViewModel이 토큰·개인 캐시·미전송 개인 작업을 정리한다. Refresh Token API가 없는 계약에서 자동 토큰 갱신을 만들지 않는다. 동의 수정 후 me를 갱신하여 모든 기능의 gating이 같은 값을 사용하게 한다. 로그아웃/탈퇴 시 다른 계정의 로컬 초안을 이어받지 않도록 사용자 ID별 저장소를 분리한다.

원문 필수 동의 4종과 v1.2의 필수2종/선택2종은 정책 차이다. 서버 계약이 확정되기 전에는 하나를 실제 적용 사실로 단정하지 않는다. 이 구조는 둘 다 수용하되 상태 판단은 계약에 맞는 한 경로로만 처리한다.

### 사진→목표→분석→루틴

사진 선택·권한 확인 → 리사이즈/형식/용량 확인 → 업로드 → photo_id 확보. 정면/측면/목표 슬롯을 구분하고 목표 photo_id를 current 입력에 섞지 않는다. image_picker 취소는 오류 메시지로 띄우지 않는다. Android 선택 중 프로세스 종료 복구도 구현 단계에서 확인한다.

목표가 있으면 목표 등록/수정 → done 확인 → 분석 POST. 목표 사진 처리 실패 시 목표 없이 진행할지 사용자에게 선택지를 준다. 목표가 없으면 분석을 바로 요청한다. 분석 접수 ID를 저장하고 2초마다 상태를 확인한다. 앱의 자동 폴링 60초 종료는 서버90초 시간 초과와 구분하며 기록에서 처리 중으로 보여준다. 백그라운드에서는 중복 폴링을 멈추고 복귀 시 즉시 상태를 읽는다.

done 결과에서 null·판정 미검증·목표 없음도 정상 화면이다. 비교 내용은 서버에서 내려온 값만 표시한다. 루틴 생성 버튼은 POST /api/routines에 analysis_id를 보내고 성공 후 주간·오늘 루틴을 갱신한다. 기존 별도 /body-comparisons API는 팀장 수정본에서 제거된 흐름이므로 연결하지 않는다.

### 운동 시작→세트→휴식→종목 종료

종목 선택 → POST /api/workout-logs(exercise_id,routine_id) → log_id/start/resumed → 실행 화면. 루틴 4종목은 서로 다른 log_id 4개다. 같은 종목이라고 다른 맥락의 로그를 재사용하지 않는다.

세트 입력은 로컬 초안이다. 완료 버튼에서 client_set_id를 만들고 요청 내용·ID를 먼저 영속 저장한 뒤 전송한다. 응답을 받으면 server set_id/version으로 매핑한다. 응답 유실은 같은 ID·같은 body를 재전송한다. 사용자가 내용을 바꾼 경우 새 ID를 만들거나 이미 저장된 세트의 PATCH로 처리하며 동일 UUID의 내용만 교체하지 않는다.

저장 대기·실패 세트는 체크 완료 상태와 구분한다. 종목 종료는 미전송 세트가 모두 동기화된 뒤 실행한다. VERSION_CONFLICT는 상세를 재조회하고 사용자가 최신 값에 대해 다시 수정하도록 안내한다. PATCH 종료 요청의 중복 방지는 서버의 완료 멱등 계약을 사용한다.

휴식 타이머는 남은 숫자만 저장하지 않고 restEndsAt을 저장한다. 다시 켜면 max(0,만료시각−현재시각)으로 표시한다. 종료 알림은 별도 로컬 알림 서비스로 예약·취소한다. 서버의 알림 설정 API·FCM 등록은 확장 단계이며 휴식 타이머 구현의 필수 의존성으로 묶지 않는다. 진동/소리/백그라운드 전달 가능성은 선택한 OS 설정과 알림 권한을 고려한다.

운동 종료·수정·삭제 후 운동 상세·기간 목록·홈 날짜 볼륨·루틴 진행·2차 통계를 갱신한다. 현재 종목 볼륨과 오늘 전체 볼륨을 혼동하지 않는다. 날짜 전체 합계는 서버 목록 summary 등 계약에 있는 집계를 사용하며 페이지에 표시된 일부 로그만 합해 전체 수치로 보여주지 않는다.

앱 복귀 시 status=in_progress 및 6시간에 걸친 KST 날짜 범위로 조회한다. 서버 started_at과 상태가 기준이다. 6시간 지난 aborted는 새로 시작을 안내하고 임의로 진행 상태로 되돌리지 않는다. 운동 실행 페이지가 닫혔다고 기록 DELETE/complete를 자동으로 호출하지 않는다.

## 4. 오류와 변경 후 갱신

| 결과·코드 | 화면 처리 | 함께 갱신할 상태 |
| --- | --- | --- |
| 401 | 토큰 정리·로그인 안내 | 세션·개인 캐시·계정별 로컬 초안 |
| CONSENT_REQUIRED | 필요한 동의만 설명, 설정 진입 | User 동의 상태 |
| GOAL_NOT_READY/GOAL_PROCESSING(제안) | 진행 상태 안내, 중복 편집 잠금 | 목표 상태 |
| ANALYSIS_NOT_READY | 생성 차단, 분석 결과 재조회 | 분석·루틴 |
| 분석 failed(HTTP200) | 코드별 재촬영/나중에 재시도 | 분석 사용량 |
| WORKOUT_IN_PROGRESS(제안) | 기존 로그 조회·이어하기/종료 선택 | 진행 로그 |
| VERSION_CONFLICT | 최신 세트 조회, 덮어쓰기 확인 없이 자동 재전송 금지 | 운동 상세 |
| 완료 세트 최소조건 위반(제안) | 마지막 완료 세트 유지·전체 기록 삭제 선택 | 운동 상세·집계 |
| AI 제안 만료/루틴 변경(제안) | 승인 비활성·새 제안 안내 | 대화 제안·루틴 |
| needs_regeneration(제안) | 이전 식사 추천 숨김, 재생성 안내 | 식단·알레르기 |
| GET404 | 삭제/비공개/없는 항목 안내 | 목록·상세 |
| 네트워크 실패 | 입력과 기존 데이터 유지, 재시도 | 서버 상태와 로컬 대기 상태 분리 |

새 필드가 없는 원문 서버를 연결할 때 execution_locked=false나 schedule_state=rest를 임의로 기본 설정하지 않는다. 판단 불가이면 재생성·승인 같은 변경 기능을 제한하거나 해당 버전 서버에서 지원하지 않는다고 표시한다. 계약 버전은 app_config의 명시 설정으로 관리하며 데이터가 빠졌다는 이유만으로 서버 버전을 추측하지 않는다.

## 5. 프론트 구현 순서

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 테마·공통 입력·버튼·SafeArea·라우터·탭 | 피그마 홈/폼을 작은 기기·키보드·글꼴 확대에서 표시 |
| 2 | 인증·동의·프로필의 가짜 Repository 연결 | 가입/로그인 분기, 뒤로 이동 입력 유지, 정확한1~7 횟수 |
| 3 | 실제 인증·프로필 API | 앱 재실행 자동 로그인, 401·중복 이메일·닉네임 처리 |
| 4 | 사진·목표·분석 입력/진행/결과/이력 | 권한 거절·pending·failed·null·측면 없음 흐름 |
| 5 | 홈·루틴·종목 선택 | 미생성·휴식·완료·진행 중·데이터 부족 구분 |
| 6 | 종목 실행·세트·휴식·로컬 복원 | 재전송 중복 없음, 저장 실패 초안 유지, 앱 종료 후 복원 |
| 7 | 날짜 기록·수정·삭제·설정·탈퇴 | 홈과 기록 동기화, 모든 계정별 캐시 정리 |
| 8 | 2차: 통계·글 분석·교정·식단·AI·커뮤니티 | 준비된 기능만 flags로 활성화 |
| 9 | 확장: 제휴·미션·할인권·푸시 | 서버 계약·운영 데이터 준비 후 연결 |

처음에는 auth/profile/home/workout의 페이지와 꼭 필요한 공통 파일부터 만든다. 모든 기능의 비어 있는 API·state·usecase 파일을 선행 생성하지 않는다. 각 기능의 Repository 계약과 같은 JSON을 쓰는 가짜 구현을 두면 BE 완료 전에도 프론트 작업이 가능하다.

## 6. BE·AI에 확인할 최소 계약

- 실제 base URL, 인증 Bearer 방식, 공통 오류 envelope, 목록 페이지·summary, 각 요청의 필수 필드.
- 목표/분석 동의·pending·타임아웃·결측값의 정확한 상태.
- 사용자당 진행 중 운동 제한, 세트 UUID·version·종료 재전송 처리.
- 주간 날짜 상태·잠금·revision 등 v1.2 제안 채택 여부.
- 탈퇴 성공이204 완료인지202 접수인지, 완료 기록 수정·삭제 후 집계의 일관성.
- 2차 Google의 실제 인증 입력과 비밀번호 재설정 딥링크 URL.

원본 ERD와 API가 다르면 프론트 모델은 실제 API 계약을 따른다. users 테이블·DB FK 구조·AI 내부 산식을 Dart에 복사하지 않는다. 신규 보완 필드를 서버가 제공하지 않으면 프론트만으로 해당 상태 보장을 구현할 수 없다는 점을 구분한다.
